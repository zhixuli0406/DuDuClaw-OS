# DuDuClaw OS — project brief for AI agents and maintainers

DuDuClaw OS is the Yocto-built appliance image line of the
[DuDuClaw](https://github.com/zhixuli0406/DuDuClaw) platform. This repo holds
the `meta-duduclaw/` Yocto layer, the frozen `appliance/` Debian/mkosi line,
and the `scripts/release-os.sh` build → smoke → package → publish pipeline.
The platform's Rust workspace stays in the platform repo and is vendored here
as trimmed snapshots (`meta-duduclaw/recipes-duduclaw/<name>/files/<name>-src/`,
regenerated by each recipe's `refresh-src.sh` from a sibling checkout —
`DUDUCLAW_CLI_SRC_ROOT` overrides the path). Never hand-edit a snapshot.

## Ground rules (inherited from the platform repo's CLAUDE.md)

1. **Verify before claiming.** A recipe or image change counts as done only
   after a real `kas build`; a boot-facing change also needs a real QEMU
   boot (`scripts/release-os.sh smoke`). `duduclaw-genericx86-64` cannot be
   booted under QEMU — say so explicitly instead of implying it was tested.
2. **Security gates fail closed.** Signature/checksum re-verification before
   publish, builder-concurrency checks, Secure Boot / verity / TPM paths:
   the unknown case must refuse, never fall through.
3. **Docs ship with the change.** Behaviour changes update `README*.md`,
   the affected component README, and `CHANGELOG.md [Unreleased]` in the
   same commit. Stale docs are bugs.
4. **Versioning.** The repo-root `VERSION` file is the OS's own semver
   (`0.x` = bring-up, `1.0.0` = first GA) and drives release artifact names
   and GitHub Release tags. It is decoupled from the embedded platform
   version (`conf/distro/include/duduclaw-platform-version.inc`) and from
   the internal Yocto `DISTRO_VERSION`.
5. **Conventional commits** (`feat(os):` / `fix(os):` / `docs(os):` …).
   Commit, tag and publish decisions belong to the maintainer.

## Documentation Classification & Placement

Same three tiers and the same decision ladder as the platform repo's
CLAUDE.md ("Documentation Classification & Placement"). Every document
(`.md`, checklist, evidence log, design note) MUST be filed by
**TYPE × CONFIDENTIALITY**. Do not drop loose files at a tree root (the
layer root, `docs/`, or the repo root outside the fixed L1 set), and never
co-locate a higher-confidentiality doc inside a lower-confidentiality tree.

### Confidentiality tiers (3 levels)

| Tier | Meaning | Git state | Lives in (this repo) |
|------|---------|-----------|----------------------|
| **L1 Public** | Product / developer docs meant to be read from the public repo or GitHub Releases | Committed, externally published | root `README.md` / `README.en.md`, `CHANGELOG.md`, `CONTRIBUTING.md`, `SECURITY.md`, `LICENSE`; `docs/<type>/`; component READMEs co-located with what they describe (`meta-duduclaw/README.md`, `appliance/README.md`, `appliance/tests/README.md`) |
| **L2 Internal** | Dev/ops material — bring-up notes, acceptance checklists, evidence transcripts, runbooks. Committed so the history is auditable, but not polished product docs | Committed (visible to collaborators) | `wiki/` |
| **L3 Confidential** | Design docs and roadmaps, commercial plans, competitive analysis, research notes, signing keys, build output | **gitignored — never committed to this public repo** | `commercial/` and `research/` (reserved, gitignored — the OS design docs currently live in the platform maintainers' private `commercial/` tree, not here), `artifacts/`, `sb-keys/`, `meta-duduclaw/.build/` |

**Hard rule:** L3 lives ONLY in gitignored trees. Before committing, confirm
no `commercial/`, `research/`, `sb-keys/`, pricing, or key material is
staged. If `git ls-files <tree>` ever returns rows for one of those trees,
untrack it with `git rm --cached -r <tree>` (files stay on disk).

### Type taxonomy → canonical home

**L1 Public — `docs/` (one subdir per type, never loose at `docs/` root; `docs/README.md` is the index):**
- `docs/architecture/` — boot chain, partition layout, update chain, trust chain
- `docs/adr/` — Architecture Decision Records (`ADR-NNN-*.md`)
- `docs/rfc/` — design proposals open for comment (`RFC-NN-*.md`)
- `docs/todo/` — public planning / tracking (`TODO-*.md`)
- `docs/guides/` — how-tos: building, flashing, real-hardware install, key management
- `docs/features/` — feature deep-dives from the user's side
- `docs/spec/` — open formats (manifest schema, update payload layout)

Create a subdir only when its first document lands. Component READMEs stay
next to the component (a layer, a recipe tree, a test library) and are
listed in `docs/README.md` under "Component references". Recipe-level
`.bb`/`.bbclass` header comments are the reference for that recipe; do not
duplicate them into `docs/`.

**L2 Internal — `wiki/`:**
- `wiki/impl/` — implementation / bring-up notes, dated in the filename (`<topic>-<YYYY-MM>.md`)
- `wiki/eval/` — acceptance checklists and test protocols, dated
- `wiki/reports/<kind>/` — evidence transcripts (QEMU boot logs, build logs). Daily reports do **not** live here — they stay in the platform repo's `wiki/reports/tl-daily/`.
- `wiki/pm/` — runbooks and tracking that are not product docs

**L3 Confidential — gitignored trees only.** Do not add design docs to
`docs/` or `wiki/` as a shortcut; if a design doc must be public, rewrite it
as an ADR/RFC under `docs/` deliberately.

### Cross-repo pointer convention

Docs here legitimately cite three trees that are not in this repo:

- `crates/...` — the platform repo's Rust workspace (public, `zhixuli0406/DuDuClaw`)
- `commercial/docs/...` and `research/...` — the maintainers' private design tree (not published)

Write such pointers as plain code spans, never as relative Markdown links,
and say which tree they refer to on first mention in a file (archived L2
notes carry a banner instead). A relative Markdown link must resolve inside
this repo.

### Vendored snapshot docs

Any `.md` under a `*-src/` snapshot (`duduclaw-cli-src/docs/README.md`,
`duduclaw-comp-src/BUILD.md`, `duduclaw-shell-src/BUILD-LINUX.md`, template
`SOUL.md` files, builtin `SKILL.md` files) is a vendored copy. Do not edit it
here — fix it in the platform repo and re-run the recipe's `refresh-src.sh`.
`appliance/skills/duduclaw-os/SKILL.md` is a shipped artifact, not a doc.

### When in doubt

1. **Is it a design doc, roadmap, commercial/competitive note, research note, or key material?** → L3 gitignored tree. Stop.
2. **Is it a bring-up note, acceptance checklist, evidence transcript, or runbook?** → L2 under `wiki/` (transcripts → `wiki/reports/<kind>/`).
3. **Is it polished product/dev documentation safe to publish?** → L1 under the matching `docs/<type>/` subdir, or the component's own README.
4. Update `docs/README.md` whenever a `docs/` or `wiki/` file is added, moved, or removed; update in-repo pointers (READMEs, recipe comments, `release-os.sh` messages) in the same commit.
