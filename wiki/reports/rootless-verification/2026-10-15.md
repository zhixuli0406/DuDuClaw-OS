**結論：不可 release。** 出廠狀態下 `duduclaw-podman.service` 開不起來（F1、F2），所以 Docker／任務沙箱／電腦操作在 rootless image 上全部不可用；就算修好這兩項，`podman run` 還會被 F3、F4 擋，`--cpus` 被 F5 擋（任務沙箱、電腦操作、discovery、script sandbox 都會帶 CPU 上限）。F6 讓 nftables restart 或 podman restart 在有容器執行時把 podman API 卡死。

Workaround（只放在 `/run/systemd/system/duduclaw-podman.service.d/`，重開機即消失，沒有寫進 image 或 repo）：

```ini
# 99-verify-workaround.conf（F2、F3、F4）
[Service]
CapabilityBoundingSet=
CapabilityBoundingSet=CAP_SETUID CAP_SETGID CAP_DAC_OVERRIDE CAP_SYS_ADMIN
ReadWritePaths=/data/duduclaw/.cache
ProtectKernelTunables=no
```

F1 的 workaround：手動 `systemd-tmpfiles --create /usr/share/duduclaw/tmpfiles.d/duduclaw-containers.conf`。另外，因 `KillMode=process`，pause process（catatonit）會跨 service restart 存活，而新的 podman 會加入它舊的 mount namespace：改 drop-in 後必須先 `kill $(cat /run/duduclaw-gateway/libpod/tmp/pause.pid)` 才會生效（第一次重試 F3 時就是被這個誤導）。

## 3. FAIL 與根因

### F1 — 首次開機（以及每次 factory reset 之後）podman unit 進入 crash loop

- 症狀：`(systemd-tmpfiles)[791]: duduclaw-podman.service: Failed to set up mount namespacing: /data/system/containers/duduclaw: No such file or directory` → `status=226/NAMESPACE`，每 5 秒重試（首次開機 `NRestarts=54`；factory reset 後重現，15:10:21 同樣訊息，`NRestarts=69`）。
- 根因：`ReadWritePaths=/data/system/containers/duduclaw`（沒有 `-` 前綴）在 namespace 建立時就要求路徑存在，連 `ExecStartPre=+` 的 tmpfiles 都在這一步失敗，所以本應建立該目錄的 tmpfiles 永遠跑不到。factory reset 會刪掉 `/data/system/containers/duduclaw`，問題每次重來。
- 要看的檔案：`meta-duduclaw/recipes-duduclaw/duduclaw-podman/files/duduclaw-podman.service:94`；修法候選：該項加 `-` 前綴，或把 `duduclaw-containers.conf` 的三行改在更早的開機階段建立（例如 `duduclaw-home-owner.service` 一起跑）。

### F2 — bounding set 太窄，setuid newuidmap 寫不進 uid_map

- 症狀：`running /usr/bin/newuidmap 1757 0 1000 1 1 100000 65536: newuidmap: open of uid_map failed: Permission denied` → `podman[...]: Error: cannot set up namespace using "/usr/bin/newuidmap"`，exit 125。第二次開機（目錄已存在）照樣發生，不是測試殘留。
- 二分結果（`systemd-run -p User=duduclaw ... podman unshare cat /proc/self/uid_map`，每次先殺 pause process）：
  - 只有 `CapabilityBoundingSet=CAP_SETUID CAP_SETGID` → open 失敗 EACCES
  - `+CAP_DAC_OVERRIDE` → `write to uid_map failed: Operation not permitted`
  - `+CAP_SETFCAP`、`+CAP_FOWNER`、`+CAP_DAC_READ_SEARCH`、`+CAP_SYS_ADMIN`（各自單加）→ 仍失敗
  - `CAP_SETUID CAP_SETGID CAP_DAC_OVERRIDE CAP_SYS_ADMIN` → 成功（`0 1000 1` / `1 100000 65536`）
  - ProtectSystem、RestrictSUIDSGID、ProtectKernelModules、ProtectKernelTunables、InaccessiblePaths、Delegate 各自單開都不影響
- 根因假設：uid_map 檔案屬於 uid 1000，euid 0 但沒有 DAC_OVERRIDE 就開不了；寫入時 kernel 要求 opener 在 parent userns 有 CAP_SYS_ADMIN（與 `kernel/user_namespace.c` `map_write()` 的檢查一致，這點是推論，沒有讀原始碼）。Mac Docker 的 off-image 檢查只看了 CapBnd 和 NNP，沒有真的跑 newuidmap。
- 要看的檔案：`duduclaw-podman.service` 的 `CapabilityBoundingSet=`，以及 `meta-duduclaw/README.md:101` 的同一句描述。podman 本身 `CapEff: 0`，擴大 bounding set 只影響 setuid 的 newuidmap/newgidmap。

### F3 — `podman run` 要寫 `$HOME/.cache/containers`，ProtectSystem=strict 擋掉

- 症狀：`Error: mkdir /data/duduclaw/.cache/containers: read-only file system`（建了目錄後變成 `open .../short-name-aliases.conf.lock: read-only file system`），每個 `podman --remote run` 都 exit 125。這個錯誤回到 API client，不會出現在 unit journal，所以清單 V8 的 journal grep 抓不到。
- 要看的檔案：`duduclaw-podman.service` 的 `ReadWritePaths=`（加 `-/data/duduclaw/.cache`，或把 `XDG_CACHE_HOME` 指到已可寫的路徑）。

### F4 — ProtectKernelTunables=yes 讓容器起不來（清單 §0 懸而未決的問題，答案是：會擋）

- bridge 網路：`netavark: set sysctl net/ipv4/ip_forward: IO error: Read-only file system (os error 30)`，exit 126。
- `--network none`：kernel `VFS: Mount too revealing`，`crun: mount proc to proc: Operation not permitted: OCI permission denied`，exit 126。
- `ProtectKernelTunables=no` 後兩者都正常（見 V8）。netavark bridge 本身可用、egress 正常，**不需要 P11（pasta mode）**。
- 要看的檔案：`duduclaw-podman.service` 的 `ProtectKernelTunables=yes`。

### F5 — kernel 沒有 CONFIG_CFS_BANDWIDTH，`cpu.max` 不存在

- 症狀：`--cpus 1.5` → `crun: open cpu.max for writing: No such file or directory: OCI runtime attempted to invoke a command that was not found`，exit 127。unit cgroup 只有 `cpu.idle cpu.stat cpu.stat.local cpu.weight cpu.weight.nice`；`/proc/config.gz`：`# CONFIG_CFS_BANDWIDTH is not set`。`--cpu-shares` 可用（`cpu.weight` = 59）。
- 影響：vendored 平台在 `task_sandbox/container.rs:509`、`computer_use_orchestrator.rs:1343`、`discovery/*`（`--cpus`）以及 `duduclaw-container/src/docker.rs:302`（`nano_cpus`）都會帶 CPU 上限，所以四種容器功能全部會失敗（API 路徑 `nano_cpus` 沒有單獨測，依同一機制推論）。
- 要看的檔案：`meta-duduclaw/recipes-kernel/linux/linux-yocto/duduclaw-rootless.cfg`（加 `CONFIG_CFS_BANDWIDTH=y`）。

### F6 — 有容器在跑時 podman unit 無法 restart，`systemctl restart nftables` 會連帶卡死

- 症狀：容器 `g1` 執行中，`systemctl restart nftables` → podman 因 `PartOf=nftables.service` 跟著 restart → `Found left-over process ... (conmon/catatonit/passt/sleep)` → `Failed to spawn executor: Device or resource busy` / `Failed to spawn 'start-pre' task` / `Result: resources`，每 5 秒重試（`NRestarts` 到 90），`podman --remote ps` 卡住。殺 catatonit/pasta 沒用（容器 PID 1 的 `sleep` 與 conmon 對 SIGTERM 不反應），要 `systemctl kill --kill-whom=all --signal=KILL` 清空 cgroup 才恢復。
- 根因假設：`KillMode=process` + `Delegate=yes`：殘留程序留在 `<unit>/supervisor` 和 `<unit>/<ctr-id>`，unit cgroup 的 `subtree_control` 已開 `cpuset cpu io memory pids`，systemd 要把新 executor 放進 unit cgroup 時撞到 cgroup v2 的 no-internal-process 規則（EBUSY）。`Restart=on-failure` 遇到 podman 自己 crash 也會卡在同一處（推論）。
- 要看的檔案：`duduclaw-podman.service` 的 `KillMode=process` / `PartOf=nftables.service`（guard 的重新載入已經有 `nftables.service.d/50-duduclaw-podman-guard.conf` 的 `ExecReload`/`ExecStartPost`，PartOf 不是必要的）。

### 觀察（不計入狀態）

- **machine-id 每次開機都換**（`2a77…` → `4f0f…` → `5fd8…` → `05ac…`）：`/etc/machine-id` 是 systemd 的 transient tmpfs bind（`Initializing machine ID from random generator`），開機 console 沒有任何 `duduclaw-persist` 訊息。`core-image-minimal-initramfs.bbappend` 只在 `DUDUCLAW_VERITY_ENABLE == '1'` 時才把 `initramfs-module-duduclaw-persist` 放進 initramfs，而這個 build（`release-linux-builder.yml`）沒開 verity。這不是 rootless 的回歸，但 V12「new /etc/machine-id」在這個 build 上沒有判別力，Relocation 的「machine-id 跨 update 不變」也要在 verity build 上驗。`/data/system/machine-id` 初次開機寫成 `2a77…` 後沒再被使用。
- gateway `CapInh: 0000000000200100`（CAP_SETPCAP + CAP_SYS_ADMIN 在 inheritable），PID 1 與 sysd 都是 0。CapPrm/CapEff/CapAmb 皆 0 且 NNP=1，目前看不出可利用路徑，但來源不明，值得查。
- sysd 在初次開機 14:23:44 拒絕了一個 `peer_uid=Some(0)` 的連線（`caller uid not authorized`），呼叫者不明。
- unit lint：`duduclaw-sysd.service:72` 與 `duduclaw-llama-server.service:66` 的 `StartLimitIntervalSec` 寫在 `[Service]`，systemd 忽略；`duduclaw-persist-seed.service:54` 的 `Documentation=` 是相對路徑，被判為 Invalid URL。
- podman journal 每次建 rootless netns 都有 `failed to move the rootless netns pasta process to the systemd user.slice: dbus: couldn't determine address of session bus`，不影響功能。
- 這個 test image 的 BusyBox 沒有 `pkill`、`comm`、`timeout`、`head -c`、`netstat`、`install`，`systemd-analyze` 也不在；清單裡用到這些的指令要改寫。
